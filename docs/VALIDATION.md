## 历史测试与当前限制

- 早期可执行诊断轮次完成过 CPU 名称、GPU 身份筛选、缺失传感器、额度轮换 / 过期等场景（一次扩展场景 182 项通过）。此后修改过单卡宽度、频率与单位对齐；**该历史结果不能代表最新代码完整回归**。
- 最新诊断探针此前被 Windows 应用程序控制阻止执行。保留拦截，不关闭安全功能，也不改名、换宿主绕过。因此新增场景只有编译验证，没有全套运行通过声明。
- 任务栏父窗口、样式与位置恢复曾通过检查，但后续鼠标命中探针出现 `childIsHitTarget=False`。这项未解决记录仍保留；用户实际可见 / 可交互的反馈不能自动抹去该诊断失败。
- 托盘箭头、截图遮罩、实际 Explorer 重启及跨屏 DPI 全套回归仍未完成。界面操作工具不可用；生产绘制的 PNG 不替代这些桌面交互验收。
- Kimi 仅有发现逻辑，真实账户额度尚未接通。单独发起官方客户端登录不等于完成 TaskbarTelemetry 集成或通过账户界面对照。
- 温度 / 频率依赖设备、驱动、权限与可选传感器后端。某个环境有数字，不能宣称所有 CPU 均支持，也不能等同独立仪器精度验证。

## 后续完整桌面验收清单

5. 验证真实 100% / 150% / 200% DPI、深浅主题、单卡与双卡设备，以及无 NVIDIA / 无额度来源。

7. 复查默认配置、隐私清理、第三方许可和 SHA-256；完整测试脚本必须在失败时停止。独立便携打包脚本只能记录实际完成的编译 / 包检查，不得把未执行的诊断记为通过。

## 2026-09-09：默认宽度不一致修正（本地待确认，未发布）

- 维护者指出 v1.0.0 排版明显变宽，并提供此前认可的 528 像素参考图。旧预览 INI 没有 `scaleWidthWithDpi`，读取结果是 `false`；发布模板却显式为 `true`。150% 下宽度因此由 528 变成 792，与问题截图一致；字号配置始终为 8.5 pt。
- 当前工作区将模板与无配置时的默认值统一为 `false`，保留显式开启宽度缩放的能力。不修改已认可的绘制槽位、字体、单 / 双卡切换或任务栏窗口机制。
- 本机使用与 v1.0.0 相同哈希的 EXE，仅在独立目录调整宽度选项后启动。原发布文件、运行包及 GitHub Release 不变；等待维护者确认恢复效果后再安排后续版本。
- 主程序和测试源码可编译；增加“模板与无配置默认值一致”的场景断言。未执行被系统阻止的诊断探针，因此不将新增断言记为运行通过。

## 2026-09-09：Codex 主动刷新（本地候选，未发布）

- 复现条件：Windows 注册的用户 / 系统 PATH 中找不到原生 `codex.exe`，但 Codex 终端临时注入的 PATH 可以找到。之前小工具只将裸命令交给 CreateProcess，自动回退本地日志后又隐藏了主动通道的错误；闲置超过 5 分钟就显示 `--%`。

- 新增原生 EXE 定位，将主动查询 60 秒与本地扫描 1 秒分开；主动快照的新鲜时限随查询周期变化，真实失败仍保留 5 分钟上限。修复旧主动快照遮住新本地事件，以及回退时丢失主动错误原因的问题。
- 保留 520 / 476 布局及其字体、留白。主程序与场景测试需编译；诊断探针仍不执行。Computer Use 窗口检查失败，错误为 `failed to launch codex app-server: 系统找不到指定的路径。 (os error 3)`，因此实际窗口与跨刷新周期验收需要本机反馈。
